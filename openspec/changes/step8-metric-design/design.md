## Context

`step8-observability-scaffold` left four metric instruments declared with no recording call sites, no label sets and provisional bucket boundaries, on the stated grounds that low-cardinality label design was itself the learning objective. This change is that work. Two of the four instruments are now recorded; two are still declared and unrecorded.

The authoritative detail lives in two places and is deliberately not repeated here. Each panel's expression, the reasoning behind it and the measurement figures it quotes live in that panel's own `description` field in `observability/grafana/dashboards/travel-agent-overview.json`, which is where a reader meets them; `observability/grafana/dashboards/README.md` covers what makes a dashboard file provisionable. This change's `tasks.md` owns the per-item history — the seeding defect's root cause, the bucket measurements, and the decisions taken along the way. A second copy of those numbers is what produced the 2026-08-11 / 2026-08-12 discrepancy already recorded there.

## Goals / Non-Goals

**Goals:**
- Make the four key metrics named in `docs/plan.md` real: recorded, labelled, and queryable.
- Keep label cardinality bounded and justified rather than incidental.
- Make a metric's absence from `/metrics` mean something definite, rather than being ambiguous between "not seeded" and "never happened".
- Give the dashboard a stable contract to build on, so panel expressions do not have to be revised every time the instrumentation changes.
- Make span names and attributes an intentional contract rather than whatever LangChain/LangGraph happen to supply, with the same cardinality and disclosure discipline already applied to metric labels.

**Non-Goals:**
- Instrumenting anything the scaffold did not already declare.
- Alerting.
- Changing the agent's behaviour. Every recording site is additive and must not alter `AgentState` or exception propagation.
- Implementing D9–D13 — deciding and specifying span naming/attributes is this change's job here; wiring them into `backend/observability/callback_handler.py` is separate, out-of-scope work.
- Implementing D14–D17 — deciding recording sites and label sets for `llm_call_duration_seconds` and `rag_retrieval_total` is this change's job here; wiring them into `backend/observability/metrics.py`, `backend/observability/callback_handler.py`, and `backend/agent/nodes.py` is separate, out-of-scope work. `backend/` is untouched by this document.
- Measuring or re-tuning `llm_call_duration_seconds`'s bucket boundaries (D16) — needs a load run against recording sites that don't exist yet, and its own authorization the same way the 2026-08-12/2026-08-19 runs had theirs. Not part of this pass.

## Decisions

### D1 — `status` carries exactly two values, `ok` and `error`
A timed-out, failed or otherwise unsuccessful request records `status="error"`; nothing else is ever produced.

This is load-bearing rather than stylistic. The dashboard's error-rate panel filters `chat_request_duration_seconds_count{status="error"}` exactly, and the latency-percentile panels filter `{status="ok"}` on the grounds that the error-rate panel still counts what they exclude. A third value would remove those requests from both. `chat-request-deadline` relies on this invariant too — its own spec forbids introducing a `status="timeout"`.

### D2 — Counters are seeded at zero; histograms never are
`seed_counters()` runs from `backend/api/main.py` after `set_meter_provider()`. Ordering is a functional requirement, not a style preference: instruments created before a provider is installed are OTel proxies, and measurements recorded on a proxy are dropped silently. Reordering imports does not fix it, because any import of the graph pulls `metrics.py` in first.

Counters are seeded because a counter that exists at zero records a starting point; without one, Prometheus first observes the series already at some value and the increase up to it is invisible to `rate()`. It also makes a query answer "0" rather than "No data".

Histograms are deliberately left unseeded. A `.record(0)` would inject a permanent observation of zero seconds that skews `histogram_quantile()` and `rate(_sum)/rate(_count)` from the first scrape onward. The consequence — that a histogram series does not exist until real traffic creates it — is accepted, and the dashboard's expressions are written to tolerate it.

### D3 — `rag_retrieval_total` keeps a label-less zero
It has no recording call sites, no label set and no panel. A label-less zero is a truthful statement that no retrieval has happened. Inventing labels for it would manufacture series that no code can ever produce. Re-seed it with real label combinations when its call sites are decided; not before.

### D4 — The dashboard is file-provisioned and two of its expressions are frozen
`observability/grafana/dashboards/travel-agent-overview.json` is a raw dashboard model loaded by Grafana's file provider, not an API wrapper object, so it can be dropped into the provisioning path and version-controlled. Confirmed provisioned on 2026-08-18 via Grafana's API reporting `meta.provisioned: true`.

The error-rate and classifier-fallback panels wrap their numerators — and only their numerators — in `or vector(0)`. That placement was verified against live data and is not open to revision; each of those two panels' `description` records why.

The heatmap panel needs two settings that nothing in its rendered output will tell you are missing: `"format": "heatmap"` on the Prometheus target, and `"calculate": false` in the panel options. The first is what makes the datasource sort series by `le` and convert Prometheus' cumulative buckets into the per-bucket counts a heatmap needs; the second stops Grafana re-bucketing values that are already bucketed. Omit either and the panel still draws — as a plausible picture in which every row above the data is darker than the one below it. It is wrong, and it does not look wrong.

### D5 — Bucket boundaries are provisional and get one measured re-tune
The scaffold's boundaries were a guess. They are re-tuned once, from an actual latency distribution, rather than repeatedly. `llm_call_duration_seconds` must not copy `chat_request_duration_seconds`'s boundaries — it measures a component of a request, not a request — and gets its own coarse set, measured, then tuned once.

### D6 — Load is generated by a committed script, not by hand
`rate()` needs several scrape intervals of data before any panel reads as anything but broken. The script's defaults are a rate limit rather than a performance setting, and its output is preserved to a file: the 2026-08-12 run's stdout was not saved, and reconstructing what happened then had to be done from Prometheus instead.

### D7 — Request-level log correlation is scoped to the application's own logger, while its span is active
`Trace and Log Correlation for a Single Request`'s original wording — "each log line it emits SHALL carry a non-null `trace_id`" — contradicted the scaffold's own `Structured Logging with Trace Correlation`, which explicitly permits a null `trace_id` for a log emitted outside any active span, "rather than causing an error." Pass 1b of the 9-d verification (2026-08-21) found a line without the request's `trace_id` on a real request: `uvicorn`'s access line for a `/chat` request, the only one of seventeen that request produced without it. The other sixteen — application-logger JSON and OTel span-export blocks alike — all carried it, and all agreed on its value.

The reason given for that line lacking a `trace_id` was wrong, and is corrected here (2026-08-22) rather than left to mislead. It was not that the line is emitted outside the request's span; uvicorn emits it from inside the ASGI send path, where the span is still current. It lacked one because `propagate=False` kept that line away from the handler carrying `TraceCorrelationFilter` — it was not JSON at all, so nothing ever stamped it. Once `uvicorn-structured-logging` routes it through that handler, the same line carries the request's `trace_id` and `span_id`. The narrowing below still stands: it turns on which lines reach the application's configured handler while a span is active, which is a boundary that holds whatever the access line happens to do.

The scenario now reads "each log line the application's own logger emits while the request's span is active," which is what pass 1b's evidence demonstrated the system actually does, and it no longer contradicts the scaffold's scenario: the one line it excludes is precisely the one the scaffold's own wording already carves out.

**This narrows a contradiction between two requirements; it does not make either requirement pass in full.** The scaffold's `Structured Logging with Trace Correlation` requirement says "the system SHALL emit backend logs in structured (JSON) format" — unqualified, covering `uvicorn.access` and `uvicorn.error` as much as the application's own logger. Item 8 of the 9-d verification recorded why they don't: both have `propagate=False` and handlers of their own, so their output never reaches `configure_logging()`'s JSON formatter at all. That output is not JSON with a null `trace_id` — the scaffold's own documented "outside a span" case — it is plain text, a different failure the scaffold's requirement does not survive as written. Rewording this change's scenario relocated the contradiction onto the scaffold's requirement rather than resolving it; that requirement is still unmet, and fixing it — reconfiguring or wrapping `uvicorn.access`/`uvicorn.error` so their output is JSON too — is left to a separate change. Do not read D7 as that requirement having been relaxed until it passed: it was never touched, and it still fails.

### D8 — Fixing D7's leftover fails by converting `uvicorn.access`/`uvicorn.error` to JSON, not by switching them off

Two ways to close the gap D7 left open. Switch the two loggers off (`access_log=False`, or silence them directly), or reconfigure them to emit JSON through the same formatter the application's own logger uses.

Switching off is cheaper, and its effect is certain — the plain-text lines item 8 found simply stop existing. It is also the more expensive choice long-term, because uvicorn's access line is currently the *only* record, at the log level, of three distinct things:
1. A request that never reaches the application's own handler at all — malformed input, a route nothing matches, anything ASGI rejects before routing ever runs the endpoint function. The application's logger never executes for these; there is nothing else to log them.
2. `/health` and `/metrics` traffic. `Self-Observation Excluded from Tracing` deliberately keeps this traffic out of spans, on purpose — so with the access log off too, it would leave no trace anywhere in the container's own output. (Prometheus's `up` series and the compose healthcheck's own pass/fail state still exist independently of logs, so this loss is partial, not total — but neither of those tells you what path or status code actually crossed the wire, which a log line does.)
3. The status code actually sent to the client, which is not always the status the handler recorded. FastAPI validates a declared `response_model` *after* the endpoint returns; if that validation fails, the client receives a `500` the handler's own code never saw, while `chat_request_duration_seconds{status="ok"}` — recorded inside the handler, before validation runs — would still read `ok`. Uvicorn's access line is the only place that specific discrepancy could ever be seen.

Converting keeps all three, and it is what Step 9's line-oriented-JSON log-shipping premise already assumes true. What it rests on has not been checked: `configure_logging()` runs at `backend/api/main.py:61`, at import time — when uvicorn imports `api.main` to resolve the ASGI callable — while `uvicorn.access`/`uvicorn.error` get their own handlers from uvicorn's own logging setup, which runs when its `Server` starts. Which one runs first, and so whether anything `configure_logging()` did to those two loggers would survive uvicorn's own setup running after it, is unverified against this repository.

**Decision: convert, not switch off.** What switching off destroys is real, and the third case is load-bearing — it is the one discrepancy this change's own metrics structurally cannot surface, because the metric is recorded before the failure that would invalidate it. The ordering question is a thing to check, not a reason to default to the lossy option: this codebase already hit the identical shape of problem in D2 (an OTel counter seeded before `set_meter_provider()` installed a real provider, silently dropped) and fixed it the same way — not by reordering imports, but by moving the dependent call out of import time into a hook guaranteed to run after the thing it depends on exists. The same move applies here: reconfigure `uvicorn.access`/`uvicorn.error` from a FastAPI startup hook rather than from `configure_logging()` at import, since a startup hook is guaranteed to run after uvicorn's `Server` has already finished its own logging setup, not before. That construction is what makes conversion trustworthy rather than merely hoped-for — but it is a plan, not yet a checked fact, and implementing it must confirm the reconfigured loggers actually emit JSON before this decision is treated as closed.

### D9 — A span name identifies an operation type, never an occurrence
`_start_span`'s `TODO` and the scaffold's own spec leave this undecided; the names in place today (`classify_intent`, `route_by_intent`, `generate_response`, `call_weather_tool`, `call_flight_tool`, `call_hotel_tool`, `retrieve_context`, `LangGraph`, `ChatGoogleGenerativeAI`) are whatever LangChain/LangGraph happen to supply via `kwargs.get("name")`/`serialized.get("name")` — incidental, not designed, per the Working Agreement's rule against blessing incidental behaviour as a requirement.

**What a span name must accomplish:** identify the *kind* of operation a span covers — which node, which call type — so a trace backend can group and filter by name meaningfully, the same way a Prometheus metric name identifies a kind of measurement. **What it must never contain:** anything derived from a specific request or response — no user input, no model output, no run-specific identifier folded into the string. A name built from request data would make every trace's span names unique, destroying exactly the grouping a trace backend's name-based views (Jaeger's operation list, Tempo's span-name rate/duration breakdowns) depend on — the identical cardinality-discipline argument D1 already applies to the `status` label and the seeding work applies to `intent`.

Judged against that, rather than designed to match it: every name LangChain/LangGraph currently supplies is a static class or function name — the same string for every invocation of that node/call type, never built from `state["user_input"]` or any other per-request value. They satisfy the requirement below as it stands, incidentally rather than by design; nothing about `_start_span` needs to override or reshape the name LangChain provides.

### D10 — Attribute set per span type: `intent` on node spans, GenAI convention keys on the chat-model span, nothing new on tool spans
An attribute earns its place only if some query would plausibly filter or group by it; everything else is cost with no return, in the same sense an unused metric label is.

- **Node spans** (`classify_intent`, `route_by_intent`, `generate_response`, `retrieve_context`, `call_weather_tool`, `call_flight_tool`, `call_hotel_tool`, and the top-level `LangGraph` span): once `classify_intent` has resolved an intent, every span opened afterward carries an `intent` attribute (see D13 for its value contract). `classify_intent`'s own span carries it too, set from its own output rather than its input, since that's the one span where it isn't known at start. Nothing else about a node earns a slot: which branch `route_by_intent` chose is already visible from which child span appears next in the trace tree (`call_flight_tool` vs. `retrieve_context` is the routing decision, structurally, with no attribute needed to restate it), and node success/failure is already carried by the span's own `Status`/`StatusCode` — `_end_span` already sets `ERROR` on exception — so a redundant boolean attribute would just be a second copy of what the span already states structurally.
- **`classify_intent` additionally carries `fallback`**, a native OTel boolean (not the string `"true"`/`"false"` `intent_classification_total`'s label is forced into by Prometheus' string-only labels — span attributes aren't so constrained, and the native type is the more correct representation, not merely a stylistic echo of the metric). Same justification as `intent`: it mirrors an existing metric dimension precisely, so it answers the same real query — jumping from an elevated fallback rate on the dashboard to an actual example trace.
- **The chat-model span** (`on_llm_start`/`on_chat_model_start` for `ChatGoogleGenerativeAI`): GenAI semantic-convention keys, per D12 — `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.operation.name`. No prompt, no completion (D11). Token usage (`gen_ai.usage.input_tokens`/`.output_tokens`) is a real, plausible query — cost/capacity tracking — and isn't user content, only a count derived from it, but whether `langchain_google_genai`'s response object reliably exposes it through the callback payload is unchecked; recorded as an Open Question rather than a spec `SHALL`, so this document doesn't mandate something implementation might not be able to satisfy.
- **Tool spans** (`on_tool_start`/`on_tool_end`): **checked, not assumed — the current codebase produces none.** `call_weather_tool`, `call_flight_tool`, `call_hotel_tool` are LangGraph *nodes* that call `get_weather`/`search_flights`/`search_hotels` as plain awaited functions, not LangChain `Tool` objects invoked through `.invoke()`/`.run()`; nothing in this graph ever fires `on_tool_start`. Live evidence bears this out: every span name observed in the container's logs falls into the chain/LLM buckets above — none named after a distinct tool-call shape. The handler's `on_tool_*` methods are live, generic infrastructure for a callback LangChain would fire if a `Tool` were ever wired in, not a currently-exercised path. The spec below states the contract for if that happens (same naming and content rules as node spans — nothing tool-specific earns a slot beyond that), rather than silently leaving an unexercised code path unspecified.

### D11 — Neither user input nor model output belongs on any span
Spans go to a console exporter today; `uvicorn-structured-logging` is making that same stream uniformly JSON, and Step 9 ships it to CloudWatch and pays for it by volume. An attribute is not a debugging convenience free of consequence — it's a line written to the same pipeline everything else in this paragraph is about.

Two distinct costs, both real: **size** — `generate_response`'s own prompt asks for "about 200 words," and `AgentState["user_input"]` is present in nearly every node's `inputs` for the whole run, so attaching either at every span that has access to it would duplicate a several-hundred-byte payload across seven-plus spans per request, all for data recoverable from a single canonical place if it were ever needed. **Disclosure** — user input is free-text end-user content, potentially naming people, places, or plans the user typed expecting it to go into a travel query, not into a trace payload that now lives in every downstream sink a trace or its export touches. Checked, not assumed: nothing in this system logs message content anywhere today — `chat request received`/`chat request completed` carry `intent`/`status`/`duration_seconds`, never `user_input` or `response`. Putting either on a span would not be continuing an existing practice; it would be the first place user content ever enters this pipeline.

**Decision: neither belongs on any span — node, chat-model, or tool — ever.** The same reasoning extends past the two things asked about to the rest of `AgentState`'s payload fields (`context`, `weather_data`, `flight_data`, `hotel_data`): they're the same shape of risk, and excluding user input/model output while leaving RAG context or a tool's raw response on spans would just move the disclosure surface sideways rather than closing it. If deeper request/response debugging is ever needed, that's a separate, explicitly-scoped decision (sampling, truncation, an opt-in debug flag) — not a default attribute.

### D12 — Adopt OpenTelemetry's GenAI semantic conventions for the chat-model span, and record the cost of doing so
The alternative to adopting the convention is inventing names (`llm.model`, `model_name`, whatever) that mean the same thing to no tool that doesn't already know this codebase. The convention's names buy interoperability with anything GenAI-aware that ever reads this data — Grafana's own LLM observability views, or any OTLP-based backend, once `OTEL_EXPORTER_OTLP_ENDPOINT` is pointed somewhere real — without a custom mapping layer.

**Decision: adopt it**, for the three attributes D10 lists: `gen_ai.provider.name = "gcp.gemini"`, `gen_ai.request.model` (the model string in use, `"gemini-3.5-flash"` today), and `gen_ai.operation.name = "generate_content"` — the last matched to Gemini's own API operation name, not the more generic `"chat"` value the convention also defines, on the evidence of the actual outbound calls this app makes (`POST .../models/gemini-3.5-flash:generateContent`, visible in this backend's `httpx` request logs).

**The cost, recorded rather than glossed over:** these attributes live under `opentelemetry.semconv._incubating.attributes.gen_ai_attributes` in the installed `opentelemetry-semantic-conventions==0.64b0` — the leading underscore is the package's own signal that nothing there carries a compatibility promise. This isn't hypothetical churn: the same installed module defines both `gen_ai.system`'s `GEMINI = "gemini"` value and its replacement, `gen_ai.provider.name`'s `GCP_GEMINI = "gcp.gemini"`, with the former's own docstring reading "Deprecated: Replaced by `gcp.gemini`" — one rename, already shipped, inside a convention still labelled experimental. Adopting it is accepting that another rename is plausible before this convention stabilizes, and that this decision will need revisiting when it does — not a one-time cost paid now.

**Implementation guidance carried here, not enacted:** the attribute *keys* this decision commits to are string values (`"gen_ai.provider.name"`, etc.) — what interoperability actually depends on. Importing the `_incubating` module's constants into `callback_handler.py` would additionally couple the code to a private import path that can move independent of the attribute names themselves. Using the literal strings, sourced from this document rather than the unstable import, gets the interoperability without that second, avoidable coupling.

### D13 — A span's `intent` attribute must agree with the metric's `intent` label, or not exist
`chat_request_duration_seconds` already carries `intent` as a label with a bounded value set (`VALID_INTENTS`, plus `unknown` on the metric's own error path — D1's `chat-request-deadline`-adjacent territory). A span attribute of the same name that could disagree with it is worse than no attribute at all: it's exactly the failure mode that makes someone distrust both the dashboard and the trace, rather than trusting either — cross-referencing a slow trace against the panel that flagged it only works if the two describe the same request the same way.

The requirement this decision produces is a constraint on *where the value comes from*, not a separate computation: every span attribute named `intent`, wherever D10 places one, is read from the same `AgentState["intent"]` field the metric recording site (`backend/api/main.py`'s `/chat` handler) already reads. Neither derives it independently. A span never sets `intent` to `"unknown"` — that value exists on the metric specifically for requests that failed *before* classification produced anything, and a span with no known intent simply carries no `intent` attribute rather than inventing a value outside `VALID_INTENTS` to fill the gap.

### D14 — `llm_call_duration_seconds` is recorded from the callback handler, not from the nodes
The callback handler already sees `on_llm_start`/`on_chat_model_start` and `on_llm_end`/`on_llm_error` for every chat-model call this app makes — `classify_intent`'s classification call, `call_weather_tool`'s city-extraction call, `generate_response`'s response-generation call — uniformly, regardless of which node initiated it. That's a structurally distinct LangChain callback event category (a different method the handler already implements), not something that needs per-node wiring to observe.

The alternative — timing each `get_model().invoke(...)` call directly in `backend/agent/nodes.py` — would touch three separate functions for what is structurally the same measurement, duplicating timing boilerplate three times, and grows to a fourth edit point the next time a node adds its own model call. It isn't forbidden by the span requirement's "no `nodes.py` changes" clause — that clause is scoped to span instrumentation specifically, and `intent_classification_total`'s existing placement inside `classify_intent` already establishes that this codebase records *some* metrics directly in nodes. But for this specific measurement, the callback handler is the more DRY site, and it's already where D9–D13 put the generically-equivalent span for the identical event — recording duration alongside a span this handler already opens and closes for the same call needs no new event hooks, only a duration value captured when that span's lifecycle already ends.

`Requirement: Metric Recording Is Additive` still holds here for the same reason it already holds for the existing span-ending code in these methods: `on_llm_end`/`on_llm_error` are void-return, side-effect callbacks LangChain invokes and does not use the return value of. A `.record()` call there touches neither `AgentState` nor the exception LangChain propagates.

### D15 — `llm_call_duration_seconds` labels: `node` and `status`
**`node`** — which enclosing node's span the LLM call happened inside: `classify_intent`, `call_weather_tool`, or `generate_response` today, the three that invoke the model (`call_flight_tool`, `call_hotel_tool`, `retrieve_context` don't, and would simply never produce a value for this label unless that changes). It doesn't need its own cardinality bound — it inherits the one D9 already put on span names, the same small closed set. The query it answers: whether classification, extraction, or generation is the slow phase of a request — a one-word classification, a short extraction, and a ~200-word generation are three structurally different prompts with no reason to share a latency distribution, so one unlabelled series would average away exactly what's worth seeing.

Getting this value is a real mechanical constraint, flagged here rather than resolved: a live `Span`'s own name isn't retrievable through the stable `opentelemetry.trace.Span` interface once created — that's an SDK-specific `ReadableSpan` property, not the ABC type this handler holds references to. The handler will need to remember node *names*, not just `Span` objects, alongside whatever it already tracks per `run_id`. An implementation detail, not a design question.

**`status`** — `ok`/`error`, recorded from `on_llm_end`/`on_llm_error` respectively: the same two-value discipline D1 already established for `chat_request_duration_seconds`, applied one level down. A slow LLM call that ultimately fails — the retry-storm shape `chat-request-deadline` exists because of — is exactly the case worth distinguishing from a slow one that succeeds; collapsing them would hide it.

Combined: 3 nodes × 2 statuses = 6 series maximum. Bounded, comparable to `chat_request_duration_seconds`'s existing 10 and `intent_classification_total`'s existing 8.

### D16 — `llm_call_duration_seconds` starts on `tasks.md`'s coarse boundary set, unmeasured
Per D5, it must not copy `chat_request_duration_seconds`'s boundaries — it measures a component of a request, not the whole request, with no reason to share a distribution with it. `tasks.md` already records the right starting point rather than inventing one here: `[0.1, 0.25, 0.5, 1, 2, 3, 5, 7, 10, 20]`, log-spaced, coarse. Adopted verbatim.

This is D5's first step, not its second. Re-tuning from an actual distribution needs a load run against the recording sites D14/D15 create — which don't exist in `backend/` yet, since this pass doesn't touch it — and, once they do, needs its own authorization the same way the 2026-08-12/2026-08-19 runs did, not something decided here on this document's own initiative. Provisional, the same way `chat_request_duration_seconds`'s scaffold boundaries were provisional before D5's own re-tune.

### D17 — D3 revisited: `rag_retrieval_total` gets a recording site and a bounded `intent` label
D3 kept a label-less zero explicitly "until its recording call sites and label set are decided." That condition is met here. D3's own text stays as the record of what was true and why when it was written; this decision supersedes it rather than rewriting it.

**Where:** `retrieve_context_node`, in `backend/agent/nodes.py` — not the callback handler. Unlike an LLM call, RAG retrieval here has no distinct LangChain callback event to hook: `retrieve_context()` (`backend/rag/retriever.py`) calls `.similarity_search()` directly, not through LangChain's `Retriever` interface, so nothing fires `on_retriever_start`/`on_retriever_end` or anything else the handler could generically intercept. The only way the handler could see this event at all would be special-casing the literal string `"retrieve_context"` against a chain span's name — matching a specific node's identity by name, a materially weaker and more accidental coupling than an LLM call's genuinely distinct callback method, and one that would break silently if that node were ever renamed, with nothing to catch it. `intent_classification_total` already sets this codebase's precedent for the other case: when something is a plain function call with no callback-visible event of its own, the metric is recorded at the call site in application code. `retrieve_context_node` is exactly that case, and the "no `nodes.py` changes" constraint doesn't reach it — that constraint is scoped to the span-instrumentation requirement, and `intent_classification_total`'s own placement in `classify_intent` is already the standing counter-example to reading it more broadly.

**When:** recorded unconditionally as the node runs, not gated on `retrieve_context()` returning successfully. That gives the counter "an attempt was made" semantics for free, with no `status` label needed: a failing retrieval still represents an attempted one, and "how often is retrieval attempted" is the more directly useful question a "RAG retrieval rate" panel answers than "how often did it succeed" — which the request's own `chat_request_duration_seconds{status}` already covers at the whole-request level. Unconditional also keeps the recording site simple: no `try`/`except` needed, nothing to get wrong about whether a partial failure should still count.

**Label:** `intent`, bounded to `VALID_INTENTS` — the same shared constant D13 already binds span attributes to, not a separately invented set. `route_by_intent` only reaches `retrieve_context` for `general` intent and for `transportation` without a flight keyword, so only two of the four values are reachable under today's routing — but the label is bound to the full constant, not hand-picked to match current routing, for the same reason D13 gives: routing logic (`graph.py`) and a metric's label domain are different code, and the domain shouldn't depend on staying in sync with routing by coincidence. `retrieve_context_node` already has `state["intent"]` available (classification always runs first) — no new plumbing needed to read it.

**Seeding:** superseding D3's bare `.add(0)`, `rag_retrieval_total` is now seeded the same way `intent_classification_total` already is — once per `VALID_INTENTS` value, at 0, from the same post-`set_meter_provider()` hook. Two of the four seeded series will likely never move under today's routing (`weather`, `hotel`) — a true statement about the system, the same kind of truthful zero D2's seeding rationale already defends, not a reason to hand-pick a narrower seed set.

## Risks / Trade-offs

- **[Risk]** Label cardinality grows silently as intents or statuses are added → **Mitigation**: `VALID_INTENTS` is a single module constant shared by the classifier and the seeding loop, so adding an intent cannot quietly desynchronise the two; `status` is fixed at two values by D1.
- **[Risk]** A histogram series that does not exist until traffic occurs makes a healthy dashboard read "No data" → **Mitigation**: the affected panel expressions guard their numerators, per D4.
- **[Risk]** The dashboard's expressions and the instrumentation's label sets are coupled but declared in different files, with nothing enforcing the link → **Mitigation**: recorded here and in the panel descriptions themselves; not automated.
- **[Risk]** Nothing under `scripts/` or `observability/` is exercised by CI, so a broken dashboard JSON or load script is only caught by hand → **Mitigation**: none in this change. Recorded as an open item.
- **[Risk]** D12's GenAI attribute names are still `_incubating` and have already renamed once (`gen_ai.system` → `gen_ai.provider.name`) inside the installed package → **Mitigation**: D12 uses the literal attribute-key strings rather than importing the unstable module, so a future rename is a value to update in one place, not an import to chase across versions; re-adopting whatever the convention settles on when it stabilizes is accepted future work, not treated as avoidable.
- **[Risk]** `intent` and `fallback` span attributes could drift from the metric labels of the same name if a future edit adds a second place either value is computed → **Mitigation**: D13 states the constraint as "read from the same field," not "compute the same way," which is the property that actually prevents drift; nothing automated enforces it beyond that being the only value either site has to read.
- **[Risk]** `llm_call_duration_seconds`'s `node` label (D15) requires the callback handler to track parent span *names*, not just `Span` objects — a small but real change to what `self._spans` holds, easy to get subtly wrong (e.g. keying the wrong `run_id`) → **Mitigation**: none beyond flagging the constraint explicitly in D15 so implementation doesn't discover it mid-edit; not implemented by this document.
- **[Risk]** `llm_call_duration_seconds`'s boundaries (D16) are adopted unmeasured and could be wrong in a way that isn't discovered until a load run happens, which this pass doesn't authorize → **Mitigation**: accepted, matching D5's own two-step process; the boundaries are explicitly provisional, not a final answer being presented as measured.
- **[Risk]** `rag_retrieval_total`'s `intent` label (D17) is bound to `VALID_INTENTS`, not to the two values `route_by_intent` currently routes to `retrieve_context` — if routing changes to reach a third value, the label handles it for free, but if routing changes so `retrieve_context` becomes unreachable for some intent it once was, that series just stops moving with nothing to flag the change → **Mitigation**: none automated; the same shared-constant discipline that prevents desynchronisation elsewhere in this document doesn't extend to "routing still reaches every value it once did," which isn't a label-cardinality problem.

## Open Questions

- **Span names and attributes — resolved as D9–D13.** Naming discipline (D9), the attribute set per span type (D10), the decision to keep user input and model output off every span (D11), GenAI semantic-convention adoption and its cost (D12), and consistency with the `intent` metric label (D13). Specified in this change's spec delta; not implemented — `backend/observability/callback_handler.py`'s `_start_span` `TODO` is unchanged by this document.
- **Whether `gen_ai.usage.input_tokens`/`.output_tokens` are obtainable from `langchain_google_genai`'s callback payload.** D10 treats this as worth capturing if available, not as a spec requirement, because it's unchecked whether the response object surfaces it through `on_llm_end`. Check before or during implementation; don't assume either way.
- **`llm_call_duration_seconds` and `rag_retrieval_total` call sites and label sets — resolved as D14–D17.** Recording site and labels for `llm_call_duration_seconds` (D14, D15), its starting bucket boundaries (D16), and `rag_retrieval_total`'s recording site, seeding, and `intent` label superseding D3 (D17). Specified in this change's spec delta; not implemented — `backend/` is unchanged by this document, and D16's boundaries are unmeasured pending a load run this pass doesn't authorize.
- **How the callback handler tracks parent span names for D15's `node` label.** Flagged as a mechanical constraint in D15, not resolved: the current `self._spans` dict holds `Span` objects, whose names aren't retrievable after creation via the stable API. Left for implementation.
- **CI coverage for `scripts/` and `observability/`.** Whether to extend `dorny/paths-filter` to those paths, and what would run if it did.
- **Whether `Prometheus Scrapes the Backend Successfully` is an addition or a supersession.** The scaffold's `Prometheus-Scrapable Metrics Endpoint` requires `GET /metrics` to return `200`. This change's requirement covers the same target but tolerates a redirect. If the backend answers `/metrics` with a redirect rather than with the metrics, the scaffold's requirement is false as written, and this one supersedes it rather than adding to it. Item 2 of the 9-d verification produces that evidence; the decision waits on it.
- **The scaffold's `Structured Logging with Trace Correlation` requirement does not hold.** Resolved as D7: `uvicorn.access`/`uvicorn.error` never reach `configure_logging()`'s JSON formatter (`propagate=False`, handlers of their own), so their output is plain text, not JSON — a requirement failure distinct from, and not excused by, the scaffold's own "null `trace_id` outside a span" allowance. This change narrowed its own request-correlation scenario so it stops contradicting the scaffold's, per D7; it does not fix the scaffold's requirement. D8 decides *how* the fix should go — convert, via a FastAPI startup hook, not switch off — but implementing and verifying it is left to a separate change.
